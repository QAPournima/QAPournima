QualityHub

Aircall · Messaging · Oct–Nov 2026

QualityHub lets anyone on the Messaging team start a staging test run from Slack and follow it to a shareable report, without touching a terminal. I built it in two parts: on-demand canary runs (live), and ticket/MR AI validate (plan live; full AI flow trialled locally).

Live

On-demand canary from Slack

Pick tests by keyword or feature, then Start or Cancel. One run at a time, queued requests wait, only the requester can cancel. GitLab CI runs the chosen canary tests on staging. A live page shows progress, then a saved report with pass/fail/skip, skip reasons, videos and Playwright traces on failures.

Plan live · AI flow local

AI validate for a ticket or MR

A Slack message starts planning: QualityHub reads the Jira ticket and MR changes, writes a senior-QA plan, and runs matching catalog tests. The full flow — plan, AI-written Playwright tests, 90s cap with 1 retry, browser-agent take-over, verdict — is built and trialled locally, not yet on main.

How a validate run works

  1. Post qualityhub validate with a ticket or MR in the QualityHub channel.
  2. Planning starts in the thread. The plan job reads the ticket and its MRs (or the MR and its ticket).
  3. The plan lists feature checks, bug repro and edge cases, each with a priority. Missing test data skips only that row and asks for the data.
  4. Matched catalog tests join the same queue and CI job as an on-demand run.
  5. AI rows (local, not on main yet) write a Playwright test per row, retry once, then hand a broken test to a browser agent.
  6. The live page and final report show Passed, Failed or Skipped with a reason. Failed means failed twice with evidence. Blocked twice is Skipped, not unfinished.

Steps 1–4 plus matched catalog tests are live. AI-written rows, agent take-over and the per-row verdict are on the unpushed branch. Planner trials were about $0.10–$0.16 per ticket.

Rules I locked in

  • Unreachable backend cases are listed as covered elsewhere (unit tests), not forced through the UI.
  • If a scenario needs data we don’t have, only that scenario stops.
  • A spend cap per validate run: remaining rows are skipped, never marked passed.
  • Validate only reads MRs. It never comments on them.
  • Reports sit behind company SSO. Traces are kept for failed tests only.

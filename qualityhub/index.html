Flagship engineering project

QualityHub and CDO are one agentic platform: two workflows, one Slack channel, one bot. Connecting the systems, designing the workflow, and shipping something engineers can run from Slack. All of this is live. Company links and tokens are left off this page.

  • LiveSlack to start a run and to receive queue, live progress and result updates in the same thread.
  • LiveJira integration for understanding requirements.
  • LiveGitHub for source, pull requests and CI pipelines.
  • LiveLLM integration for reasoning and test planning.
  • LivePlaywright for deterministic web execution.
  • LiveNative mobile tests on a device connected to a laptop (USB or Wi-Fi).
  • LiveBrowser agent for investigating failures.
  • LiveBudget, safety and evidence — cost caps, Failed vs Skipped rules, traces and a shareable report.

The problem

Teams now build with AI, and on many of those teams the QA role is gone. The live safety net is an automation suite that covers only part of the app. Fast changes still need a check, and another team still needs a way to run that suite on a build.

Before

  • Development moved to AI, and the people who used to own validation left with it.
  • What stayed live was the existing automation suite, and it covered only part of the app.
  • A non-regression run meant asking the owning team to trigger it on their build, then waiting.
  • A team with no QA had no one to check a ticket, and no place the new check was kept for the next change.

After

  • An engineer asks QualityHub to test a merge request or a ticket, or uses the Slack form to run non-regression and see that fast development left the app intact.
  • The same Slack form drives an automation framework the team already built. That run uses the existing suite. Any team starts it on the build, with no wait for the owners to trigger it.
  • CDO covers validation for a team that has no QA. The AI-driven workflow runs the check, saves the scenario it created, and QualityHub can run that saved scenario later.

Not a test runner. A platform.

QualityHub sits between how people work (Slack, Jira, pull requests) and how software is proven (Playwright for web, Appium for the mobile app on a laptop-connected device, GitHub CI, traces, reports). Humans stay in control: who can cancel, what data is missing, what is Failed versus Skipped, and when AI is allowed to spend.

Accessible

Slack form or qualityhub validate. No terminal. Queue, duplicates and cancel are first-class.

Intelligent

Planner reads the ticket and pull request, writes coverage, data limits and priorities. Models are routed per step.

Evidence-driven

Live progress, pass/fail/skip with reasons, videos and Playwright traces on failures. Failed means failed twice with evidence.

One agentic platform · separate workflow · live

CDO, the QA assistant on the ticket

This is already how a ticket is handled. One ticket gets one coordinator and two plain test runners. The CDO agent thinks and decides. Frontend QA and Backend QA only run checks and return a result. A pass or fail always comes from a real test. It uses the same bot in #quality_hub and does not open the QualityHub form. Every run is then saved under that application.

Architecture and stack — CDO

Nine steps on every ticket. The same suite runs at three moments — local, the staging web app, and staging after deploy. Only the target and where the evidence lands change. Blue steps wait for your reply. The merge request is a manual step: it is created only when you reply ok in Slack after local validation. Any other reply restarts the fix from that message. Each run is saved under that application's folder.

Scenarios, per application

Every automation run is saved as a test scenario in a folder named for that application. A new application gets a new folder, and the scenarios start there. The next CDO task on that application reads this folder first.

Auto-healing

If a saved scenario fails, or the product has moved on, the agent updates or replaces that scenario. What the run showed is saved as knowledge, and the next task on the same application starts from it.

Case type

Each ticket is ui, api, or both. That picks the main check. Backend runs first: it is faster, and a broken API makes the UI result meaningless. both stops on the first failure. There is no type that skips QA.

One status, one line in Slack

Only the CDO agent writes the ticket status: assigned, running, passed, failed, or needs you. The thread gets one line, for example Task status: backend local: passed; frontend local: running.

The agent starts a runner with one JSON request and reads one JSON result. It checks that the result belongs to this ticket, stage, and build before trusting it. A timeout is needs you, and it is not retried in the same run.

You stay in control

At each gate the agent waits for ok / approve, change, more details, or skip. The word you used is stored with the date. After the local test, only ok creates the merge request. Any other Slack reply restarts the fix from that message. In #quality_hub, as a whole message:

  • stop CDO — CDO work waits. Tickets already in progress stay where they are. Direct asks still run.
  • resume CDO — CDO starts again from where it stopped.
  • status CDO — replies whether CDO is running or stopped, and which tickets are in progress.

Customer data changes are human-only. Production is read-only. Runners never receive the agent’s Jira or Slack credentials. CDO runs on weekdays, 08:00 to 19:00 UK time, and each Claude step has a spend cap.

One suite, three targets, one evidence trail

The same Playwright suite and the same report. Only the target and where the evidence lands change.

Step 5 · Local

Target: the local build. Runs unit tests and the Playwright suite against the change. Writes the report, video and screenshots.

Step 7 · Staging web app

Target: the staging web app for that merge request. The same suite runs again. Fresh evidence is posted on the MR and in Jira.

Step 9 · Post-merge

Target: real staging, once the deploy is green. The same suite runs again. Fresh evidence is posted on the MR and in Jira.

Step 6 creates the merge request only after you reply ok. Step 8 hands the draft to human review. Any other reply after local validation restarts the fix from that message.

AI does the work. Humans keep the gate.

Two flows, two answers. On a ticket, Claude investigates, proposes the fix, runs the tests and drafts the evidence. Every gate — go / no-go, creating the merge request, posting anything the team can see — waits for you. The standing suite is different: Claude may have written the scenario once, and the run itself is plain Playwright.

Per-ticket workflow

Claude is involved throughout: investigating, proposing the fix, running the tests, drafting evidence for the MR and Jira. Go / no-go, MR creation and any team-visible post wait for an explicit reply. Nothing ships on its own.

Standing watch

No model calls while the suite is running. Claude helped write the scenarios once. The runs are deterministic Playwright, on a GitHub CI schedule when that schedule is on.

Example

You gave the background and a first proposed fix. The agent cross-checked it against the real code and countered with a refinement. You agreed the final fix together. It ran the local suite, then drafted the MR and the Jira comment. Nothing was posted until you said go ahead.

Written once with Claude. On the hourly schedule it ran as plain Playwright on GitHub CI and caught a real regression, with no model in the loop. It still runs on demand.

A real regression, caught

While the hourly schedule was on, every run since the afternoon before had one scenario failing. The others passed. The failing step was a click that timed out. It was flagged automatically, hour after hour, with no one watching for it directly.

AI planning, generation and agent take-over

Validate is one flow. Catalog tests cover what already exists. AI rows cover the rest. A passing test goes to its verdict. A test that fails twice goes to the browser agent.

Plan

Reads the Jira ticket and pull request changes. Writes feature checks, bug repro and edge cases, each with a priority. Missing data skips only that row and asks for the data. Unreachable backend cases are marked covered elsewhere, not forced through the UI.

Generate, run, take over

Writes a Playwright scenario per AI row. 90 seconds, one retry. A broken test is handed to a browser agent. Classify product bug versus test bug. Summarise a verdict for reviewers. Remaining rows skip when the run budget is reached — never marked passed.

Model routing and cost

Each step uses the cheapest model that can do it. Any step can be switched with an environment variable, no code change. Planner trials: about $0.10–$0.16 per ticket.

Engineering decisions

  • One agentic platform, two workflows — QualityHub starts a test; CDO assists on the ticket, saves the scenario under that application, and keeps what the run taught it.
  • One platform, two entry points — form for canary, validate for a ticket or pull request.
  • Failed = failed twice with evidence. Blocked twice = Skipped, with the reason. No unfinished rows.
  • Validate only reads pull requests. It never comments on them.
  • Only the person who asked can cancel, through a private button.
  • Traces only for failed tests. Reports behind SSO.
  • Humans stay in the loop: AI proposes, automation executes, people own the verdict rules and the budget.
